# Where Are You — MVP 規格

> 本文件是 2026-08-09 設計訪談的產出，記錄每一項決策與**為什麼**排除其他選項。
> 實作若要偏離本文件，先回來改這裡。

App 名稱：**Where Are You**
Bundle ID：`com.chienchuanw.whereareyou`
平台：iOS 18+ / SwiftUI / SwiftData / Swift 6.3 / Xcode 26.6

---

## 1. 產品定位

幫使用者回答兩個問題，而且要在**三秒內**：

1. 「這東西最後一次在哪？」 — 被動查詢
2. 「包包裡該有的東西都在嗎？」 — 出門前核對

**服務規模假設：一個使用者 20–80 件高價值物品**（會搞丟的、很重要的、出門必帶的）。
不是全屋資產盤點工具。因此不做批次匯入、條碼掃描、OCR、CSV。

## 2. 資料模型

### 2.1 Node — 唯一的實體

**一切都是 Node。** 沒有「容器」與「物件」之分：任何 Node 都能裝下另一個 Node。

```swift
@Model final class Node {
    var id: UUID = UUID()
    var name: String = ""              // 必填，識別主鍵
    var note: String = ""              // 自由備註（取代「分類說明」）
    var parent: Node?                  // 目前實際在哪
    var home: Node?                    // 歸屬地：本來應該在哪（選填）
    var isPinned: Bool = false         // 是否釘在首頁
    var photoFilename: String?         // 檔案在 Documents/，DB 只存檔名
    var createdAt: Date = Date()
    var updatedAt: Date = Date()
}
```

**為什麼統一遞迴而不是「空間 → 容器 → 物件」三層：**
容器自己會移動。登山包被帶去公司時，裡面的充電線位置必須自動跟著走。
三層固定模型無法表達「包中包」、也無法讓包包自己擁有位置歷史。

**為什麼不區分 isContainer：**
「筆袋」到底算容器還是物品？這個決定對使用者沒有意義卻必須做。
改成：**有子節點的 Node 在 UI 上就是可展開的容器**，建檔時少填一欄。

**為什麼沒有 tags / category：**
使用者原本說的「分類」就是收納空間本身。容器階層即分類。
跨容器查詢（「所有充電線在哪」）靠名稱搜尋解決，不值得為此多一張關聯表 + 一套標籤管理 UI。

**為什麼沒有 quantity：**
數量與位置模型直接衝突 — 三條充電線分別在包包、車上、書房，`quantity = 3` 要掛在哪個節點？
20–80 件高價值物品本來就幾乎都是單件。需要區分就用名稱（「充電線(USB-C 短)」）。

### 2.2 MoveEvent — 移動歷史

```swift
@Model final class MoveEvent {
    var id: UUID = UUID()
    var node: Node?
    var from: Node?                    // nil = 建檔
    var to: Node?
    var at: Date = Date()
    var latitude: Double?              // 當下 GPS（選填）
    var longitude: Double?
    var placemark: String?             // 反向地理編碼後的地名，如「信義區」
    var photoFilename: String?         // 現場照（選填）
}
```

**為什麼存完整歷史而不是只存 `lastMovedAt`：**
「回想最後一次在哪」常常需要往回看不只一步。而且誤操作可還原、日後要做「常去哪」分析不必重建資料。
寫入成本極低。

### 2.3 CloudKit 相容性（重要）

MVP **只存本機、不開同步**，但模型從第一天就遵守 CloudKit 限制：

- 所有純量屬性都有預設值
- 所有關聯都是 optional
- 不使用 `@Attribute(.unique)`
- 照片存檔案系統，DB 只存檔名

之後只要加 `.cloudKitDatabase(.automatic)` 就能開多裝置同步，不需要痛苦的 schema 遷移。

## 3. 核心運算語意

以下四項是最容易寫錯的地方，全部要有單元測試。

### 3.1 遞迴計數

容器 C 顯示的「N 件」= `subtree(C)` 中**所有子孫**的數量（不含 C 自己）。

### 3.2 缺件（missing）

```
missing(C) = { n : home(n) ∈ subtree(C) 且 parent-chain(n) ∉ subtree(C) }
```

**只有東西離開整棵子樹才算「缺」。**

範例：`上班包 → 筆袋 → 鑑子筆`，橡皮擦 `home = 筆袋` 但目前直接躺在上班包裡 →
**不算缺**，因為東西還在包裡，出門情境不該為此警示。

**為什麼不用 `now ≠ home`：**
那會讓「東西在包裡只是沒放回筆袋」變成假警報，徽章很快就會被使用者忽略。

### 3.3 外來件（foreign）

```
foreign(C) = { n : parent-chain(n) ∈ subtree(C) 且 home(n) ≠ nil 且 home(n) ∉ subtree(C) }
```

顯示為 `○`，不計入「缺 N」。`home == nil` 的物件永遠不算缺、也不算外來。

### 3.4 循環防呆

`parent` 不得設為自己或自己的任一子孫。移動前必須檢查，違反則拒絕並提示。

## 4. 畫面與流程

### 4.1 首頁

```
我的東西

搜尋物件

釘選
登山包                8 件   缺 2
上班包                6 件   缺 1

地點
家                   42 件
書房                  18 件
公司                   5 件
車                     5 件
```

無卡片、無分隔線、無 chevron，也**不用 emoji** —— 容器的識別靠名稱與強調色，
不靠圖示。分群只由群組標籤與間距造成。對照 Figma `Screens — Light / Home`。

首頁 = **所有根節點（`parent == nil`）+ 所有 `isPinned` 的節點**。

**為什麼需要 isPinned：**
登山包的 parent 通常是「家/儲藏室」，若首頁只列根節點，最高頻的動作（出門前核包）反而藏得最深。
一個 Bool 解決。

搜尋列固定在頂部，同時服務「找東西」情境。

### 4.2 容器盤點頁（主要更新入口）

```
登山包                          8 件 · 缺 1
────────────────────────────────
✓ 頭燈                    home=登山包
✓ 水壺                    home=登山包
✗ 雨衣                    home=登山包 · 在陽台
○ 充電線                  home=書房抽屜
```

- `✓` 在這裡且歸屬正確
- `✗` 歸屬在此但人不在 → 缺件
- `○` 人在這裡但歸屬別處 → 外來件

**點任一列的狀態圖示即切換「在 / 不在」**，切成「不在」時彈出 sheet 問「它在哪？」。

**為什麼以盤點為主要更新入口而非單筆編輯：**
使用者不會在搬動物品的當下開 app。他是在「出門前核包」時才發現資料要修。
把更新做在他自然會來的那個畫面，而不是要他事後回想著去搜尋每一件。

單筆編輯仍可從詳細頁進行，但不為它做優化。

### 4.3 「它在哪？」sheet

選新位置，選項排序：最近使用的容器 → GPS 推測的當前地點底下的容器 → 完整樹狀瀏覽 → 搜尋。

### 4.4 物件詳細頁

名稱、備註、照片、目前位置、歸屬地、以及**完整移動歷史時間軸**：

```
08/09 20:20   書房抽屜 ← 登山包    · 信義區
07/22 09:14   登山包 ← 保險箱      · 大安區
06/01 11:03   建檔於保險箱
```

### 4.5 新增物件

```
名稱  [ 頭燈           ]   ← 唯一必填
位置  [ 登山包      ▾ ]   ← GPS 推測預設值
歸屬  [ 同上         ▾ ]   ← 預設等於位置
照片  [ ⊕ 之後再拍     ]
備註  [                ]
```

**為什麼照片選填：**
目標是「8 件裝備 60 秒建完」。強制拍照會讓每件變成 15–30 秒，建到第 5 件就放棄。
照片是輔助回想，不是識別主鍵 — 名稱才是。

## 5. GPS 的角色

權限：**When-In-Use only**。

- 建檔 / 移動時自動抓一次座標，寫進 `MoveEvent`，反向地理編碼成地名
- **主要價值是降低輸入摩擦**：人在家 → 新增物件時預設容器就從「家」底下最近用過的挑
- 次要價值：表達「東西臨時放在某個非容器的地方」（掉在某咖啡廳）

**不做**背景定位、地理圍籬、Always 權限。

## 6. 明確不做（MVP 非目標）

| 項目 | 原因 |
|---|---|
| 提醒 / 通知（離家提醒、定期盤點） | 提醒的前提是資料新鮮。資料是否會被維護還沒驗證，不新鮮的提醒只是噪音。且要 Always 定位 + 背景執行 + 通知三層權限。 |
| CloudKit 多裝置同步 | 模型已相容，開關留著。MVP 不處理登入態、衝突、配額。 |
| 分享 / 家庭共用 | 需要帳號系統與後端。 |
| 條碼 / QR / NFC 標籤 | 服務規模只有 20–80 件，貼標的成本高於效益。 |
| 標籤 / 多重分類 | 見 §2.1。 |
| 數量欄位 | 見 §2.1。 |
| 批次匯入 / CSV / OCR | 見 §1 規模假設。 |

## 7. 刪除語意

刪除一個有子節點的 Node → **子節點上移到祖父層**（`deleteRule: .nullify` + 手動 reparent）。

絕不連帶刪除。沒有雲端備份的情況下，一次誤觸不該蒸發幾十筆資料。

**被上移的子節點各寫一筆 `MoveEvent`。**

理由：§2.2 存歷史是為了「回想最後一次在哪」與「誤操作可還原」。不寫的話，筆的歷史
最後一筆停在「移入筆袋」，但筆袋已經不存在、筆現在在上班包，中間那一步是斷的 ——
而刪錯容器正是最需要被追溯的誤操作。

歷史記錄的是**東西在哪**，不是**誰移動的**，所以系統造成的位置變更同樣要入帳。

被刪節點若是別人的歸屬地，那些 `home` 一律清成 `nil`，不留懸空參照。歸屬地的變更
不寫 `MoveEvent` —— 那是「應該在哪」的變更，不是位置變更。

## 8. 工程設定

### 專案結構（XcodeGen）

```
where-are-you/
  project.yml                    ← 進版控
  docs/SPEC.md
  Sources/
    App/         WhereAreYouApp.swift
    Models/      Node.swift, MoveEvent.swift
    Logic/       TreeQueries.swift（遞迴 / 缺件 / 循環防呆）
    Views/       HomeView, ContainerView, ItemDetailView, AddItemView, WhereIsItSheet
    Services/    LocationService, PhotoStore
  Tests/
  .gitignore                     ← 排除 *.xcodeproj
```

`.xcodeproj` **不進版控**，避免 pbxproj 衝突；`xcodegen && xcodebuild build` 即可驗證。

### 測試策略

只測邏輯層，用 Swift Testing + in-memory `ModelContainer`：

- 遞迴計數包含孫節點
- 缺件計算：離開子樹才算缺（含 §3.2 的橡皮擦反例）
- 外來件計算
- 移動到自己的子孫會被拒絕
- 刪除容器後子節點上移到祖父

不寫 UI Test — 對單人 MVP 太脆、太慢。

## 9. 視覺方向（v2）

> v1 曾走「iOS 原生為骨」，做出來太像系統設定 App，已作廢。
> 現行方向參考 Uber / Untitled UI / MiLi MiTag 的簡約語言。

**白底、Inter、零卡片、零分隔線、零 chevron。**

層級完全由**字重、尺寸與間距節奏**撐起，不靠灰底分組、不靠框線。
綠色只出現在三個地方：主按鈕、「在」狀態記號、移動歷史的當前節點。

| 決策 | v1（作廢） | v2（現行） |
|---|---|---|
| 底色 | 灰底 `#F2F2F7` + 白卡片 | 整面純白，無卡片 |
| 分隔 | 每列 hairline | 零分隔線，靠 56pt 列高與群組間距 |
| 字型 | SF Pro 全域 | Inter 走拉丁與數字，中文用系統黑體 |
| 列高 | 44pt | 56pt |
| chevron | 每列都有 | 全部移除，整列即觸控目標 |
| 群組標題 | iOS 區段標題 | 12/16 Semi Bold + 1.6 字距 |
| 表單 | 左標籤右值同列 | 標籤在上、值在下，底線一條 hairline |
| 歷史 | 條列 + 分隔線 | 左側時間軸，當前節點用強調色 |

### 不使用 emoji（硬規則）

介面、程式碼、文件一律不用 emoji。容器圖示、狀態指示、按鈕圖示全部走**向量字符**
（`Icon/Glyph` 元件，24×24 線性、可 tint、可綁 token）。

理由：emoji 無法 tint、深色模式下對比不可控、跨系統版本外觀會變、無障礙朗讀結果雜亂，
而且尺寸與線寬跟 SF Symbols 對不齊。使用者自訂容器的識別改用「圖示 + 強調色」，不用 emoji。

### Token（v2 實際值）

| Token | Light | Dark | 對比 |
|---|---|---|---|
| `bg/grouped`（畫面地） | `#FFFFFF` | `#0B0C0D` | — |
| `bg/field` | `#F3F4F5` | `#17191B` | — |
| `bg/elevated`（sheet） | `#FFFFFF` | `#16191A` | — |
| `text/primary` | `#111315` | `#F2F4F4` | 18.6 / 17.7 |
| `text/secondary` | `#6B7278` | `#9BA1A8` | 4.88 / 7.51 |
| `text/tertiary` | `#6F757B` | `#8A9198` | 4.66 / 6.14 |
| `text/danger` | `#C9251C` | `#FF6F63` | 4.84 / 6.38 |
| `border/separator` | `#EDEEEF` | `#212426` | 1.16 / 1.25 |
| `accent` · `state/ok` | `#2F6F4E` | `#4CAF7D` | 5.99 / 7.21 |
| `state/missing` | `#C9251C` | `#FF6F63` | 5.58 / 7.18 |
| `state/foreign` | `#6F757B` | `#8A9198` | 4.66 / 6.14 |

字級：Inter — Large Title 30/35 Bold · Title 2 21/27 Bold · Title 3 19/25 Semi Bold ·
Headline 17/23 Semi Bold · Body 17/23 Medium · Subhead 14/20 · Footnote 13/18 ·
Caption 12/16 Semi Bold +1.6 字距（群組標籤與表單標籤專用）。

**層級不靠亮度差，靠尺寸與字距。** `text/tertiary` 與 `text/secondary` 亮度接近是刻意的 ——
在零分隔線的版面裡，群組標籤是唯一的分組訊號，淡到看不清等於沒有分組。

**唯一刻意不合規的項目**：`border/separator` 對比 1.16。它是欄位底線與時間軸的裝飾性邊界，
不承載狀態辨識（標籤與值本身承載），拉高會讓畫面重新變得吵。這是有意識的取捨。
