# Where Are You — MVP 規格

> 本文件是 2026-08-09 設計訪談的產出，記錄每一項決策與**為什麼**排除其他選項。
> 實作若要偏離本文件，先回來改這裡。

App 名稱：**Where Are You**
Bundle ID：`com.chienchuanw.whereareyou`
平台：iOS 18+ / SwiftUI / SwiftData / Swift 6.3 / Xcode 26.6

---

## 1. 產品定位

幫使用者回答兩個問題，而且要在**三秒內**：

1. 「這東西最後一次在哪？」 — 被動查詢
2. 「包包裡該有的東西都在嗎？」 — 出門前核對

**服務規模假設：一個使用者 20–80 件高價值物品**（會搞丟的、很重要的、出門必帶的）。
不是全屋資產盤點工具。因此不做批次匯入、條碼掃描、OCR、CSV。

## 2. 資料模型

### 2.1 Node — 唯一的實體

**一切都是 Node。** 沒有「容器」與「物件」之分：任何 Node 都能裝下另一個 Node。

```swift
@Model final class Node {
    var id: UUID = UUID()
    var name: String = ""              // 必填，識別主鍵
    var note: String = ""              // 自由備註（取代「分類說明」）
    var parent: Node?                  // 目前實際在哪
    var home: Node?                    // 歸屬地：本來應該在哪（選填）
    var isPinned: Bool = false         // 是否釘在首頁
    var photoFilename: String?         // 檔案在 Documents/，DB 只存檔名
    var createdAt: Date = Date()
    var updatedAt: Date = Date()
}
```

**為什麼統一遞迴而不是「空間 → 容器 → 物件」三層：**
容器自己會移動。登山包被帶去公司時，裡面的充電線位置必須自動跟著走。
三層固定模型無法表達「包中包」、也無法讓包包自己擁有位置歷史。

**為什麼不區分 isContainer：**
「筆袋」到底算容器還是物品？這個決定對使用者沒有意義卻必須做。
改成：**有子節點的 Node 在 UI 上就是可展開的容器**，建檔時少填一欄。

**為什麼沒有 tags / category：**
使用者原本說的「分類」就是收納空間本身。容器階層即分類。
跨容器查詢（「所有充電線在哪」）靠名稱搜尋解決，不值得為此多一張關聯表 + 一套標籤管理 UI。

**為什麼沒有 quantity：**
數量與位置模型直接衝突 — 三條充電線分別在包包、車上、書房，`quantity = 3` 要掛在哪個節點？
20–80 件高價值物品本來就幾乎都是單件。需要區分就用名稱（「充電線(USB-C 短)」）。

### 2.2 MoveEvent — 移動歷史

```swift
@Model final class MoveEvent {
    var id: UUID = UUID()
    var node: Node?
    var from: Node?                    // nil = 建檔
    var to: Node?
    var at: Date = Date()
    var latitude: Double?              // 當下 GPS（選填）
    var longitude: Double?
    var placemark: String?             // 反向地理編碼後的地名，如「信義區」
    var photoFilename: String?         // 現場照（選填）
}
```

**為什麼存完整歷史而不是只存 `lastMovedAt`：**
「回想最後一次在哪」常常需要往回看不只一步。而且誤操作可還原、日後要做「常去哪」分析不必重建資料。
寫入成本極低。

**歷史同時存名稱快照，不只存參照。**

`MoveEvent` 除了 `node` / `from` / `to` 三個關聯，另存 `nodeName` / `fromName` / `toName`
三個字串。空字串在 `fromName` 代表建檔、在 `toName` 代表移到頂層。

理由有兩個，第二個是硬性的：

1. **歷史是只增不改的紀錄，不該因為容器被刪就掉資訊。** 「書房抽屜 ← 登山包」在登山包
   被刪之後仍然要讀得出來，否則 §4.4 的時間軸會出現無法解讀的空白。刪除容器正是最
   需要回溯的情境，卻剛好是資訊被抹掉的情境，這說不通。
2. **不存快照的話，程式會當掉。** 三個關聯必須在 `Node` 上宣告對應的 inverse 並設
   `deleteRule: .nullify`，否則節點被刪除並存檔後再讀 `event.to`，SwiftData 會拋
   `This model instance was invalidated because its backing data could no longer be
   found in the store`。inverse 補上之後參照會安全地變成 `nil` —— 但那也代表參照本身
   靠不住，所以顯示一律以名稱快照為準，關聯只用於「該節點還在時可以點進去」。

快照凍結在事件寫入的當下，**之後不再同步**。所以把容器改名之後，舊的歷史條目會繼續
顯示舊名稱。這是刻意的：歷史講的是「當時那個東西叫什麼、在哪」，不是「它現在叫什麼」。
實務上改名比刪除常見得多，這個後果要先講清楚，免得被當成 bug。

### 2.3 CloudKit 相容性（重要）

MVP **只存本機、不開同步**，但模型從第一天就遵守 CloudKit 限制：

- 所有純量屬性都有預設值
- 所有關聯都是 optional
- 不使用 `@Attribute(.unique)`
- 照片存檔案系統，DB 只存檔名

之後只要加 `.cloudKitDatabase(.automatic)` 就能開多裝置同步，不需要痛苦的 schema 遷移。

## 3. 核心運算語意

以下四項是最容易寫錯的地方，全部要有單元測試。

### 3.1 遞迴計數

容器 C 顯示的「N 件」= `subtree(C)` 中**所有子孫**的數量（不含 C 自己）。

### 3.2 缺件（missing）

```
missing(C) = { n : home(n) ∈ subtree(C) 且 parent-chain(n) ∉ subtree(C) }
```

**只有東西離開整棵子樹才算「缺」。**

範例：`上班包 → 筆袋 → 鑑子筆`，橡皮擦 `home = 筆袋` 但目前直接躺在上班包裡 →
**不算缺**，因為東西還在包裡，出門情境不該為此警示。

**為什麼不用 `now ≠ home`：**
那會讓「東西在包裡只是沒放回筆袋」變成假警報，徽章很快就會被使用者忽略。

### 3.3 外來件（foreign）

```
foreign(C) = { n : parent-chain(n) ∈ subtree(C) 且 home(n) ≠ nil 且 home(n) ∉ subtree(C) }
```

顯示為 `○`，不計入「缺 N」。`home == nil` 的物件永遠不算缺、也不算外來。

### 3.4 循環防呆

`parent` 不得設為自己或自己的任一子孫。移動前必須檢查，違反則拒絕並提示。

## 4. 畫面與流程

### 4.0 導覽

首頁是根，其他畫面都是從它推進去的。被推進去的畫面**在大標題上方帶一個返回鍵**
（Figma `NavBar` 的 `Back` 屬性），首頁沒有。

**為什麼不用 iOS 內建的返回鍵：**
v2 的大標題是自繪的（§9），畫面沒有系統導覽列可以掛返回鍵。留著系統導覽列會多出一條
它自己的底線與高度，正好是 v2 要拿掉的東西。

**為什麼不改用 Inline 導覽列（它本來就有返回鍵）：**
盤點頁的標題是容器名稱，是這一頁最重要的一行字。降成 17pt 的 inline 標題會讓
「我現在在哪個包裡」變成畫面上最不明顯的資訊，而那正是使用者點進來的理由。

**為什麼不只靠邊緣滑動返回：**
可用但不可發現。返回是這個 app 除了點列以外唯一的導覽動作，不該藏在手勢裡。

### 4.1 首頁

```
我的東西

搜尋物件

釘選
登山包                8 件   缺 2
上班包                6 件   缺 1

地點
家                   42 件
書房                  18 件
公司                   5 件
車                     5 件
```

無卡片、無分隔線、無 chevron，也**不用 emoji** —— 容器的識別靠名稱與強調色，
不靠圖示。分群只由群組標籤與間距造成。對照 Figma `Screens — Light / Home`。

首頁 = **所有根節點（`parent == nil`）+ 所有 `isPinned` 的節點**。

**為什麼需要 isPinned：**
登山包的 parent 通常是「家/儲藏室」，若首頁只列根節點，最高頻的動作（出門前核包）反而藏得最深。
一個 Bool 解決。

搜尋列固定在頂部，同時服務「找東西」情境。**唯一的例外是一件東西都還沒有的時候** ——
那時整支搜尋列不出現，見 §4.1a。

#### 4.1a 首頁的三個狀態

| 狀態 | 條件 | 畫面 |
|---|---|---|
| 一般 | 有節點，且搜尋列是空的 | 搜尋列 + 釘選 / 地點兩組 |
| 空 | 一個節點都沒有 | 不放搜尋列，改放「還沒有任何收納空間」，動作是建立第一個空間 |
| 搜尋 | 搜尋列有字 | 兩組收起來，改列搜尋結果；沒有結果就放「找不到「X」」，動作是直接建立「X」 |

對照 Figma `Home — Empty` 與 `Search — No Results`。

**為什麼空的時候不放搜尋列：**
搜尋列在這支 app 裡是「找東西」的入口，而不是裝飾。一個節點都沒有時它搜不到任何東西，
擺著只是要使用者先讀懂一個沒有作用的控制項，再往下找到真正該做的那件事。
空狀態只該有一個動作，那個動作就是建第一個空間。

**為什麼搜尋時把釘選與地點兩組收起來，而不是把結果接在下面：**
搜尋是「我現在只想看這個」的動作。把結果疊在原本的兩組下面，使用者得先滑過一整頁
他此刻不關心的東西。這也是為什麼找不到時要直接給出建檔動作 —— 搜尋落空的下一步
幾乎一定是「那就現在建一筆」。

### 4.2 容器盤點頁（主要更新入口）

```
登山包
5 件 · 缺 1 · 8 月 9 日更新

✓ 頭燈
✓ 水壺
✗ 雨衣
  在陽台
○ 充電線
  歸屬在書房抽屜
✓ 急救包
```

對照 Figma `Screens — Light / Container — Inventory`。

**點任一列的狀態圖示即切換「在 / 不在」**，切成「不在」時彈出 sheet 問「它在哪？」。

**為什麼以盤點為主要更新入口而非單筆編輯：**
使用者不會在搬動物品的當下開 app。他是在「出門前核包」時才發現資料要修。
把更新做在他自然會來的那個畫面，而不是要他事後回想著去搜尋每一件。

單筆編輯仍可從詳細頁進行，但不為它做優化。

#### 4.2a 這一頁到底列出哪些東西

列表 = **直接子節點 ∪ `missing(C)`**（`missing` 的定義見 §3.2）。

缺件必須列出來，即使它已經不在這個容器裡 —— 否則 `✗` 這個狀態根本沒有列可以掛。
「雨衣的歸屬地是登山包但人在陽台」正是出門前最需要看到的那一行，把它藏起來等於
把整頁最有價值的資訊刪掉。

**只列直接子節點，不遞迴展開。** 標頭的「N 件」是遞迴的（§3.1），但列表不是。
理由：包中包要能被點進去自己的盤點頁，攤平會讓「筆袋」這一層消失，使用者也就無法
在筆袋自己的頁面上核對筆袋。標頭回答「總共帶了多少」，列表回答「這一層有什麼」。

**點一列（記號以外的地方）進的是那個東西的詳細頁**（§4.4c），不是它的盤點頁 ——
即使它有子節點。筆袋的盤點頁從筆袋的詳細頁再進一層。理由見 §4.4c：
一條規則涵蓋所有列，容器才不會到不了自己的詳細頁。

一個節點同時是子節點又是缺件在定義上不可能（缺件的前提是 parent-chain 不在子樹裡），
所以聯集不需要去重規則。

#### 4.2b 每一列的狀態與副標

| 狀態 | 判定 | 記號 | 副標 |
|---|---|---|---|
| 在 | 人在這裡，且 `home` 是 `nil` 或落在這棵子樹裡 | `✓` | 無 |
| 缺 | 落在 `missing(C)` 裡 | `✗` | 「在 <目前所在的容器名>」，頂層則寫「不在任何容器裡」 |
| 外來 | 落在 `foreign(C)` 裡 | `○` | 「歸屬在 <home 的名稱>」 |

`home == nil` 的東西顯示為 `✓` 而不是另一種狀態。它既不算缺也不算外來（§3.3），
再多一種記號只是要使用者去理解一個對他沒有意義的區別。

**為什麼副標不寫成 `home=登山包` 這種鍵值格式：**
盤點是掃視動作，不是閱讀動作。`✓` 已經說完「該在這、也在這」，再補一句 `home=登山包`
是純冗餘；而 `✗` 與 `○` 各自缺的那一塊資訊不同 —— 前者要知道「那它跑去哪了」，
後者要知道「那它該回哪」。兩種狀態各補各的那一句，比統一格式更省眼力。

#### 4.2c 排序

單一列表，依名稱排序（`localizedStandardCompare`），不依狀態分組。

`localizedStandardCompare` 會**跟著裝置語言變**，中文在不同 locale 下的先後不一樣。Figma 的
mock 用的是截圖基準機（模擬器）的順序 —— 兩邊對不上時先確認是不是 locale 差異，那不是 bug。

**為什麼不把缺件排在最前面：**
盤點是一邊核對一邊切換狀態的過程。依狀態排序會讓使用者每按一次記號、那一列就跳走，
核到一半找不到剛才看到哪裡。缺件的顯眼程度由紅色記號承擔，不需要再靠位置強調。

#### 4.2d 標頭行

`<遞迴件數> 件 · 缺 <缺件數> · <最後更新日期>更新`

- 缺件數為 0 時整段「· 缺 N」不出現，不寫「缺 0」
- 日期取這個容器與其子孫之中最新的 `updatedAt`，格式為當地的「M 月 d 日」
- 空容器（無子節點且無缺件）改顯示「還沒有東西」，見 Figma `Container — Empty`

**東西「離開」這個容器也要算進日期。** 一次移動同時改動兩個容器的內容 —— 舊的少一件、
新的多一件 —— 所以 `move` 要把**兩邊的容器**都標記成剛動過，不能只標記被搬的那一個。

少了這條會出現這一頁最不該有的畫面：使用者把水壺從登山包拿出去（水壺沒有歸屬地，
所以它既不在子樹裡也不算缺件），件數從 5 掉到 4，日期卻還停在上個月。§4.2d 存在的
唯一理由就是不讓「舊資料」被讀成「現在的狀態」，結果它自己在剛寫入之後就先說謊。

**為什麼要有最後更新日期：**
盤點資料的價值完全取決於新鮮度。一份三個月沒動過的清單，`✓` 代表的是「三個月前在」，
不講出來的話使用者會把它讀成「現在在」，那比沒有資料更危險。

#### 4.2e 點狀態記號會發生什麼事

記號是這一頁唯一的寫入動作。三種狀態按下去的結果不一樣：

| 目前狀態 | 切成 | 結果 |
|---|---|---|
| `✓` 在 | 不在 | 開「它在哪？」sheet（§4.3），選完目的地才真的移動 |
| `○` 外來 | 不在 | 同上 —— `○` 的東西人也在這裡 |
| `✗` 缺 | 在 | 直接移進這個容器，不開 sheet |
| `✗` 缺，但移進來會成環 | — | 記號不可點 |

**最後那一列是什麼情況：**
缺件的定義（§3.2）只要求「歸屬在這棵子樹裡、人在子樹外」，沒有排除「它其實是這個容器的
祖先」。`收納箱` 的歸屬地填成 `儲藏室`、而 `儲藏室` 本身放在 `收納箱` 裡，就同時滿足兩者 ——
`收納箱` 會出現在 `儲藏室` 的清單上，標成 `✗`。

按下去要做的事（把 `收納箱` 移進 `儲藏室`）違反 §3.4，`move` 一定會拒絕。與 §4.3b 同一條
原則：**一個按了一定會失敗的控制項不該是可按的**。所以這一列的記號不給觸控回饋，也不
寫歷史 —— 而不是讓使用者一直按、一直沒有反應。

這個狀態是使用者自己把歸屬地填錯造成的，要修得去詳細頁改歸屬地。這一頁不負責救它。

**為什麼 `✗` 不開 sheet：**
目的地已經確定了 —— 使用者正站在那個容器的盤點頁上按「它在這」。再彈一次 sheet 問
「移到哪」，等於要他重講一次剛剛已經說完的話，而且第一個要排除的選項還正好是這一頁。

**為什麼 `○` 與 `✓` 同一邊，而不是自成一種切換：**
記號切的是**位置**（人在不在這裡），不是**歸屬地**。`○` 講的是歸屬地在別處，那是另一個
維度的事，不該綁在同一個手勢上。改歸屬地要去詳細頁。

切換一律寫 `MoveEvent`（§2.2）。使用者把 sheet 收掉則什麼都不發生 —— 記號回到原狀、
不寫歷史。「我想改但還沒決定改成什麼」不是一次移動。

**已知缺口：存檔失敗目前不會告訴使用者。** 移動會先改記憶體、畫面立刻更新，之後才存檔。
存檔失敗（磁碟滿、裝置鎖著取不到受保護資料）只會寫進 log，使用者看到的是一次成功的更新，
重開 app 卻回到舊位置 —— 而他信任這份清單的理由正是「我剛剛核過」。

要補的是一個錯誤提示的設計，那還沒有畫，也就還不能實作（`CLAUDE.md` 的 Figma 先行）。
在補上之前，這裡刻意**不**用「移動失敗就把畫面改回去」來假裝沒事：資料確實已經改了，
只是沒落地，把畫面回捲會變成第三種與真實狀態都不符的說法。

### 4.3 「它在哪？」sheet

從盤點頁把一件東西切成「不在」時彈出。標題是 `<名稱>移到哪？`，底下是搜尋列與一列到底的
位置選項，選一個就移動並關閉。對照 Figma `Screens — Light / Container — Where is it?`。

#### 4.3a 選項的組成與排序

單一列表，不分段標題，依序是：

1. **最近用過的容器** —— 取自 `MoveEvent` 的 `to`，新到舊、去除重複（語意見 §4.4b）。
   右側標一句「最近用過」
2. **其餘所有可選容器** —— 依名稱排序（`localizedStandardCompare`），右側無標記
3. **「不放在任何容器裡」** —— 固定在最後一列，代表移到頂層

第 1 組**最多 3 個**。它是捷徑，不是另一份清單 —— 超過三個之後，使用者得先讀完一整段
才知道要不要往下找，那跟直接往下找已經沒有差別，卻多花了一次判斷。

**上限套用在 §4.3b 的排除之後，不是之前。** 先砍到三個再排除，會讓最近用過那一組莫名
其妙地變成兩個、一個、甚至零個 —— 把東西移出 `登山包` 時，`登山包` 自己與它底下的
`急救包` 都會被排除，於是三個名額被兩個不能選的佔掉，第四新的 `陽台` 明明合格卻不會遞補。
使用者看到的是「最近用過只有一個」，而他昨天才用過三個。

**為什麼不用區段標題把前兩組分開：**
兩組是同一種東西（可以放進去的地方），差別只在「你最近用過它」。那是一句補充，不是一個
分類。區段標題會讓使用者以為要先決定「我該從哪一組挑」，但他要的只是掃過去看到那個名字。
右側的「最近用過」把這句補充掛在該掛的那一列上，不多花一整行。

**為什麼要有「不放在任何容器裡」：**
§4.2b 的 `✗` 副標已經會寫「不在任何容器裡」，代表頂層是一個顯示得出來的狀態 —— 卻沒有
任何入口可以設成它。東西掉在路上、借出去、丟了，這些都不在任何容器裡，而使用者當下最
想記下的就是「它不在包裡了」。逼他隨便挑一個容器只會把資料弄髒，而髒掉的那一筆正是
之後最需要回溯的那一筆。

#### 4.3b 哪些容器不出現在選項裡

- **自己，以及自己的所有子孫** —— §3.4 的循環防呆。防在選單這一層而不是選完才報錯：
  一個選了一定會失敗的選項，不該出現在選單上
- **目前的 parent** —— 把東西移到它已經在的地方不是一次移動（與 §4.4b 排除同一個容器
  的理由相同）
- **本來就在頂層的東西，不出現「不放在任何容器裡」那一列** —— 同一條理由。從盤點頁開的
  sheet 不會遇到這個情況（§4.2e 開得起 sheet 的兩種狀態都代表東西人在這個容器裡），
  但這條語意屬於選項本身，不該靠呼叫端剛好不會踩到來成立

沒有子節點的節點**仍然是合法的目的地** —— 一切都是 Node（§2.1），「筆袋」在裝進第一支筆
之前不會長得跟別的東西不一樣。若把選項限制成「已經有子節點的」，每個容器第一次要被用到
的那一次都選不到。

#### 4.3c 搜尋列

第 2 組是「幾乎每一個節點」，所以這支 sheet 一定要有搜尋列，不是加分項。

行為與首頁的搜尋（§4.1a）對齊，這樣兩個地方只需要學一次：

| 狀態 | 畫面 |
|---|---|
| 搜尋列是空的 | 最近用過 → 其餘容器 → 「不放在任何容器裡」 |
| 搜尋列有字 | 三段全部收起來，只列符合的候選（仍套用 §4.3b 的排除規則） |
| 有字但沒有符合的 | 「找不到「X」」，**沒有**建立新容器的動作 |

比對規則沿用 §4.4b 的搜尋語意（名稱與備註、不分大小寫、依 `updatedAt` 由新到舊）。

**為什麼沒有符合時不給「建立「X」」：**
首頁搜不到會給建檔動作，因為那裡的下一步就是建一筆新的。這裡不一樣 —— 使用者正在
回答「這東西移到哪」，順手長出一個空容器只會多一個沒人維護的節點。真的需要新地方，
先把 sheet 收掉。

#### 4.3d 這一版還沒做的兩段

本節早期的版本把排序寫成「最近 → GPS 推測的地點底下 → 完整樹狀瀏覽 → 搜尋」。搜尋已經
是 §4.3c，剩下兩段：

- **GPS 推測的地點** —— 需要 `LocationService`（§5），尚未實作。它是**排序的優化，不是選項
  的來源**；沒有它，使用者仍然選得到每一個容器，只是好的猜測不會自己浮上來
- **樹狀瀏覽** —— 收斂進第 2 組的攤平清單。樹狀瀏覽要求使用者先知道東西在樹的哪一層，
  那正是他打開這個 app 想避免的事；而攤平清單加上搜尋，抵達任何一個節點都是同樣的兩步

**這裡曾經寫錯過，留著當記號：** 早期版本把 sheet 內搜尋一起延後，理由是「§1 的規模假設
是 20–80 件，攤平的清單掃得完」。那句話把「有幾件東西」跟「有幾個可選的目的地」當成同一個
數字了 —— 因為葉節點也是合法目的地，兩者其實相等，光是種子資料就有 57 列、要滑九個畫面。
規模假設限制的是資料量，不是清單長度。

### 4.4 物件詳細頁

一個 Node 的完整檔案。對照 Figma `Screens — Light / Item — Detail`。

```
護照

目前位置
書房抽屜

歸屬地
書房抽屜

備註
效期 2031 / 04

移動歷史
書房抽屜 ← 登山包
8 月 9 日 20:20 · 信義區

登山包 ← 保險箱
7 月 22 日 09:14 · 大安區

建檔於保險箱
6 月 1 日 11:03
```

名稱是大標題，不是欄位 —— 它是這個 Node 的識別主鍵（§2.1），
降成一個標籤在上、值在下的欄位會讓它跟備註一樣重。

#### 4.4a 這一版是唯讀的

顯示以上全部，**但都還不能改**。原因是管線（`CLAUDE.md`）：Figma 現行的
`Item — Detail` 三列都是純值列，沒有任何修改的入口，而視覺要先在 Figma 成立。

**這件事有代價，要講明白：** §4.2e 寫著「改歸屬地要去詳細頁」，而這一版的詳細頁
還做不到。那句話在編輯做出來之前指向一個到得了、但改不動的畫面 —— 比原本指向一個
不存在的畫面好，但仍然是個缺口。編輯是下一支 PR，屆時位置與歸屬地走
`WhereIsItSheet`（§4.5d 已經證明它是共用的位置選擇器），備註要先在 Figma 補一支
多行輸入元件。

**照片區塊在 `PhotoStore` 做出來之前不出現在這一頁上**，與 §4.5a 同一條理由：
一個佔著位置、按了沒反應的區塊，比沒有那個區塊更糟 —— 它承諾了一個不存在的功能。
對照 Figma `Item — Detail`（現行，無照片）與 `Item — Detail — With Photo`（之後切回去）。

#### 4.4c 怎麼抵達，以及怎麼從這裡去盤點頁

**盤點頁的每一列都通往詳細頁**，不分它有沒有子節點。詳細頁多一列「裡面有 N 件」，
點它才進那個容器的盤點頁。N 用遞迴件數（§3.1），與首頁、盤點頁標頭同一個數字。

**那一列永遠出現，不設任何條件** —— 包括 N 是 0 的時候，讀作「裡面有 0 件」。

這條規則試過兩個比較「聰明」的版本，兩個都會生出到不了的畫面，原因是同一個：
**§2.1 拒絕區分容器與物件**，所以任何條件都等於偷渡那個區分回來，而被條件擋掉的那些
節點，它們的盤點頁就沒有入口了。

- 用「有沒有子節點」—— 一個包被帶出去、裡面的東西又各自被拿走，它的子節點是空的，
  但歸屬在它底下的東西仍然會以 `✗` 列在它的盤點頁上，而那正是使用者要把它們
  一件一件標回來的地方
- 用「盤點頁列不列得出東西」—— 剛建好的空容器兩邊都是空的，於是它的盤點頁到不了，
  而**那一頁正是把第一件東西放進去的入口**（§4.2d 空容器的「加入第一件」）。
  容器建好之後就再也放不進東西，這比排版怪嚴重得多

所以不設條件。「裡面有 0 件」看起來怪，但它是真的，而且點進去永遠有意義：
不是看到東西跑去哪了，就是把第一件東西放進來。與 §4.2d 的標頭同一個立場 ——
那裡也是「0 件 · 缺 2」，不會因為 0 就假裝這個容器不存在。

那一列放在**三個欄位之後、移動歷史之前**，列高與其他列一致（`size/row`），
沒有 chevron（§9）。順序的理由是這一頁由上而下在講一個故事：
這是什麼（標題）→ 它在哪（三個欄位）→ 它裡面有什麼 → 它經歷過什麼。
夾在欄位中間會把「位置 / 歸屬地 / 備註」這個與 `Item — Add` 對齊的區塊拆開。

**為什麼不是「有子節點的走盤點頁、沒有的走詳細頁」：**
那樣的話容器永遠到不了自己的詳細頁。登山包正是最需要詳細頁的那一類 —— 它自己也會
移動、也有歷史（§2.1 統一遞迴的理由），而 §4.2e 那個「收納箱的歸屬地填成儲藏室」
的死結，要修就得打開 `收納箱` 的詳細頁改歸屬地，而 `收納箱` 是個容器。
一條「列 → 詳細頁」的規則沒有這個死角，代價只是包中包多一次點擊。

**首頁的「釘選」與「地點」仍然直接進盤點頁**，不改。那兩組列的角色是「我要核這個包」，
不是「我要看這個東西的檔案」；它們長得也不一樣（帶件數與缺件徽章）。
出門前核包是最高頻的動作，不該為了規則整齊而多一次點擊。

**這條決定留下兩個缺口，都在 §4.4f。** 一是除了搜尋以外，本節列的每一條路都沒有通往
「沒有歸屬地的根節點」自己的詳細頁，因為那種節點不會以子節點的身分出現在任何盤點頁的列上。
二是**這條規則自己造成的**：「地點」與「釘選」都可能把一個盤點頁是空的節點送進盤點頁，
而下一段正要說明那是一個該被消滅的死路。

**但首頁的搜尋結果通往詳細頁**，與盤點頁的列一致。搜尋是「我在找這個東西」，
下一步是看它在哪、看它的歷史 —— 那是詳細頁。而且搜尋比對的是名稱與備註（§4.4b），
撈出來的多半是葉節點；把葉節點送進盤點頁，使用者會看到一個寫著「還沒有東西」的空畫面，
那正是 §4.4c 要消滅的死路。搜尋結果與那兩組共用同一種列，但**去處不同**。

#### 4.4d 三個欄位各自顯示什麼

| 欄位 | 值 | 空的時候 |
|---|---|---|
| 目前位置 | `parent` 的名稱 | `parent == nil` 寫「不在任何容器裡」 |
| 歸屬地 | `home` 的名稱 | `home == nil` 寫「未設定」 |
| 備註 | `note` | 空字串、或只有空白字元時整列不出現 |

**位置與歸屬地即使是空的也要留著那一列**，因為它們是這個 app 的核心語意 ——
「沒有歸屬地」是一個關於這件東西的事實（它永遠不算缺、也不算外來，§3.3），
不是一個缺漏。把列藏起來會讓使用者以為這一頁沒講完。

**備註空的時候整列不出現**，理由相反：備註沒有語意，它就是一段自由文字（§2.1）。
「只有空白字元」算空的 —— 與 §4.5a 判定名稱有沒有填是同一條規則，
使用者看不出一格空白與真的空白有什麼不同，不該只有其中一種會讓那一列冒出來。
一列寫著「備註」然後底下空著，只是告訴使用者「這裡可以填東西」—— 而這一版還不能填。

#### 4.4e 時間軸

**顯示一律以 `MoveEvent` 的名稱快照為準，不讀關聯**（§2.2）。關聯在節點被刪除後會
被清成 `nil`，只有快照撐得住；關聯只用在「該節點還在時可以點進去」，而那是編輯
那一版的事，這一版不點。

每一筆兩行。上行是發生了什麼，下行是時間與地點：

| `fromName` | `toName` | 上行 |
|---|---|---|
| 有 | 有 | `<toName> ← <fromName>` |
| 空（建檔） | 有 | `建檔於 <toName>` |
| 有 | 空（移到頂層） | `不在任何容器裡 ← <fromName>` |
| 空 | 空 | `建檔，不在任何容器裡` |

空字串的語意見 §2.2：`fromName` 空代表建檔，`toName` 空代表移到頂層。

**為什麼移到頂層也用箭頭，而不是寫成「移出登山包」：**
每一列同一個形狀，眼睛只要學一次 —— 箭頭左邊永遠是「這次移動之後在哪」。
「移出 X」是唯一一列讀起來像動詞片語的，而且它把「那現在在哪」這個問題丟回給使用者。
「不在任何容器裡」這句話在 §4.2b 的 `✗` 副標與 §4.3a 的選項裡已經用過兩次，
第三次沿用它比新造一個說法便宜。

下行是 `M 月 d 日 HH:mm`，`placemark` 不是 `nil` 時再接 ` · <地名>`。
日期格式與 §4.2d 的標頭同一個，理由也同一個：同一支 app 裡的日期只該有一種長相。

**排序依 `at` 由新到舊。** `at` 相同時要有穩定的第二鍵（用 `id`）——
不穩定的排序會讓同一頁在兩次開啟時列出不同的順序，那看起來就像資料自己在變。

**最新的那一筆，下行走 `text/accent`，其餘走 `text/secondary`。**
這就是 §9 說的「移動歷史的當前節點用強調色」：最新那一筆的目的地就是它現在在的地方。

**用「最新的那一筆」而不是「`to` 等於現在的 `parent` 的那一筆」來判定**，
因為後者要讀關聯，而關聯靠不住（§2.2）；而且位置變更一律寫歷史（§4.2e、§7），
所以最新那一筆的目的地在定義上就是現在的位置。位置若曾經在不寫歷史的情況下被改過，
那是那條路徑的 bug，不該由這一頁用一套平行的判定去補償 —— 那只會把 bug 藏起來。

**歷史不會是空的**：建檔一定寫一筆（§4.5c），被上移的子節點也一定寫一筆（§7）。
真的空了代表寫入路徑漏了，這一頁**顯示「還沒有任何紀錄」而不是崩潰或留白**，
因為那是一個要被看見的異常，不是一個正常狀態。

#### 4.4f 兩個已知的導覽缺口：到不了的詳細頁，與通往空頁的列

盤點頁列出的是**直接子節點 ∪ 缺件**（§4.2a），兩者分別要求 `parent` 或 `home` 不是 `nil`。
根節點的 `parent` 依定義是 `nil`，所以**它不會以子節點的身分出現在任何一頁的列上** ——
只有在它自己也填了歸屬地時，它才會以 `✗` 出現在那個歸屬地的盤點頁上（根節點沒有
parent-chain，所以它一定落在別人的子樹外，§3.2 的另一個條件自動成立），而歸屬地是
選填的（§4.5a）。**而且不只那一頁** —— `missingItems` 把 `homedItems` 攤平在整棵子樹上，
所以它會同時列在那個歸屬地的每一個祖先頁上。唯一的例外是它自己也是那個歸屬地的祖先
（§4.2e `收納箱` 的形狀）：那時它落在自己的子樹裡，`missingItems` 會濾掉它，
所以它不會出現在自己那一頁上。這不影響底下的結論（缺口一講的是 `home` 為 `nil` 的節點，
它一列都不會有），寫出來只是免得日後被當成漏算。

首頁的「釘選」與「地點」兩組則通往盤點頁（§4.4c），不是詳細頁。

**缺口一：`home` 是 `nil` 的根節點，它自己的詳細頁沒有任何導覽入口，只有搜尋到得了。**
種子資料裡的家、書房、公司、車、登山包全部落在這一類。

這件事在詳細頁那一段其實已經被寫進程式碼，只是被當成截圖問題解掉了 —— `RootView` 的
`-open-item` 之所以要能全庫搜尋，理由正是「頂層節點不在任何容器的列裡，
沒有這條路的話登山包這種根節點的詳細頁就到不了」。那是一個 debug 啟動參數，
不是使用者走得到的路。

**這不只是「看不到一頁」而已。** 登山包自己也會移動、也有歷史，那正是 §2.1 統一遞迴的
理由；而唯一看得到那段歷史的地方就是它的詳細頁（§4.4e）。使用者要問「這個包上禮拜在哪」，
得先想到用搜尋。

**缺口二：首頁的列通往盤點頁，而空的盤點頁回答不了使用者帶來的問題。**
被 §4.3a 移到頂層的雨衣會出現在「地點」（§4.4b），點下去是它的盤點頁 —— 它沒有子節點
也沒有缺件，所以那一頁整段走空狀態。§4.4c 說明搜尋結果為什麼要走詳細頁時，寫的正是
「把葉節點送進盤點頁，使用者會看到一個寫著『還沒有東西』的空畫面，那正是 §4.4c 要消滅的
死路」。同一段推論當初沒有套用到首頁那兩組，因為那時看起來沒有東西會把葉節點放進去。
**實際上有三條路都會，診斷時三條都要看：**§4.3a 的「不放在任何容器裡」把東西移到頂層；
§4.5b 的「建立第一個空間」直接建一個沒有子節點的根節點；§7 的刪除把子節點上移到祖父層，
而被刪的若是根節點，祖父層就是頂層（`Node.delete` 把 `child.parent` 設成 `grandparent`，
根節點的 `grandparent` 是 `nil`），同時把歸屬在它底下的東西的 `home` 清成 `nil`。
**§4.4b 與 §4.4c 目前互相矛盾，矛盾就在這裡。**

**實際的畫面比那句引文更糟。** 除了標頭那句「還沒有東西」，空狀態還放了標題
「這個包還是空的」與說明「加入你出門一定要帶的東西，之後就能一眼確認有沒有漏。」——
對一件剛被記成「不在包裡」的雨衣，那兩句直接斷言它是個包，並邀請使用者往裡面塞裝備。
（**這兩句目前只存在於程式碼**，§4.2d 只定死了標頭那一句。動作標籤「加入第一件」也一樣 ——
而 §4.4c、§4.5b、下面那一段，以及 `Sources/Logic/ItemDetail.swift` 與
`Tests/ItemDetailTests.swift` 的註解，都把 §4.2d 當成它的出處 —— **五個引用目前全部指空，
其中兩個在程式碼裡**，補 §4.2d 的時候只掃 SPEC 會漏掉它們。空狀態的標題、說明與動作標籤
應該一起在 §4.2d 講明並與 Figma `Container — Empty` 對齊 —— 那是另一個要補的洞。
**這一支刻意不順手補**，理由不是範圍潔癖：那支 frame 已經畫好了，所以要補的不是
「把程式碼的字抄進 SPEC」，而是先確認 frame 與程式碼的字一不一樣、不一樣時哪一邊算數。
那是一個設計判斷，屬於那支畫面自己的 PR ——
管線是 SPEC → Figma → 程式碼，不能從最右邊倒補。）

**「地點」不是唯一會這樣的一組，「釘選」同樣會，而且不限頂層。**
§4.4b 的「釘選」是所有 `isPinned` 的節點、不管它在樹的哪一層，而 §4.4c 讓兩組都通往盤點頁。
釘一個盤點頁是空的節點（例如護照）就複製出同一條死路，而它根本不在頂層。
**所以缺口二的界線不是「頂層」，也不是「沒有子節點」，是「首頁的列指向一個空的盤點頁」。**
沒有子節點並不保證那一頁是空的：把登山包裡的東西全部搬走，它自己變成葉節點，但雨衣
（歸屬在它底下）仍然以 `✗` 列在那一頁上，那一列就不是死路。這與 §2.1 一致，
它本來就不該用節點在樹上的位置來分類。現在還看不到，只因為釘選還沒有切換的入口
（`isPinned` 只在種子資料與測試裡被設過），那是尚未實作，不是不會發生。

**兩個缺口長得很像，但不是同一個 —— 分開講是因為混在一起就會誤診。**
缺口二**不需要**缺口一成立：種子資料裡的雨衣歸屬在登山包，所以它移到頂層之後會以 `✗`
列在登山包的盤點頁上，它的詳細頁其實到得了（缺口一對它不成立），但**從首頁點下去那一條路
仍然什麼都沒回答**。一個講的是「這一頁到不到得了」，一個講的是「這一條路把使用者送去哪」。
兩個由同一個修法解掉（見下），但診斷時不要互相代入。

**缺口二與 §4.4c「『裡面有 0 件』點進去永遠有意義」不衝突，差別在使用者帶著什麼問題來。**
§4.4c 講的是「我要把第一件東西放進去」—— 那時空盤點頁就是入口，「加入第一件」（§4.2d）
正是他要的。這裡講的是「我剛剛才說雨衣不在包裡了，那它現在算什麼」—— 同一頁對這個問題
一個字都沒回答，而使用者是被首頁那兩組列送過去的，不是自己選擇要加東西。
那一頁沒有變得沒有意義，是那一條路把問題送錯了地方。

**§4.2e 那個死結兩個缺口都不屬於，不要弄混。** 那裡的前提是 `收納箱` 的歸屬地填成了
`儲藏室`，而 `儲藏室` 本身放在 `收納箱` 裡 —— 所以 `收納箱` 的 parent-chain 落在
`儲藏室` 的子樹外，§3.2 兩個條件都成立，它會以 `✗` 列在 `儲藏室` 的盤點頁上，
點那一列就到得了 `收納箱` 的詳細頁。（**光有歸屬地不夠**：護照歸屬在書房抽屜、人也在
書房抽屜，它顯示的是 `✓`。這一節開頭對根節點講的是完整版本，這裡不能只講一半。）
所以「要修得去詳細頁改歸屬地」那句話是成立的，卡住的是編輯還沒做
（§4.4a），不是到不了。

**修法的形狀：盤點頁補一個通往「這一頁主角自己的詳細頁」的入口，無條件、不分它有沒有
子節點** —— 也就是 §4.4c 那一列的鏡像。

**那一列必須連空狀態那一版一起做，否則兩個缺口都只解掉一半。這一條是硬性的，不是偏好。**

缺口二的每一個實例依定義都落在空的盤點頁上（雨衣沒有子節點也沒有缺件，
`ContainerInventoryView` 在 `rows.isEmpty` 時整段換成空狀態），所以只把那一列加進
「有列的版面」，缺口二一件都沒解到 —— 而畫面會看起來像已經修好了。

**缺口一也一樣，而這件事特別容易漏掉，因為上面舉的例子會誤導。**
拿來說明缺口一的五個種子根節點全部都有子節點，看起來缺口一只發生在「有列的版面」上。
但 §4.5b 的首頁「建立第一個空間」建出來的，正是一個**沒有子節點、`home` 也是 `nil`
的根節點**（`NewItemDraft(.firstPlace)` 走 `init(location: nil)`，而歸屬地預設跟著位置走）。
所以**剛裝好 app、剛建完第一個空間的那一刻，使用者唯一擁有的那個節點就是缺口一的實例，
而它的盤點頁是空的**。那不是邊角案例，那是新使用者的起始狀態。

**但那個節點不是缺口二**，這一點要分清楚：使用者當下的意圖正是要把東西放進去，
空狀態的「加入第一件」就是他要的下一步 —— 上面那條 §4.4c 的立場對它完全成立。
兩個缺口在這一類節點上重疊的是**版面**，不是判定：缺口二要求那一列出現在空狀態，
而缺口一在這一類節點上剛好也要求同一件事，理由卻不同。
分清楚是因為下一支 PR 會拿這一段當依據 —— 把它讀成「空狀態一律是死路」，
就會回頭去改 §4.4c 那個立場，而那個立場是對的。

兩個都解掉之後，雨衣顯示「0 件」才可以照 §4.4b 說的繼續接受，因為點下去不再是死路。

**為什麼不是把首頁的「地點」列改成通往詳細頁：**
§4.4c 已經回答過 —— 那兩組列的角色是「我要核這個包」，出門前核包是最高頻的動作，
不該為了規則整齊而多一次點擊。而且那兩組的列長得不一樣（帶件數與缺件徽章）。

**為什麼不是「盤點頁列不出東西時才補那個入口」：**
那是條件，而任何條件都等於偷渡 §2.1 拒絕的區分（§4.4c 已經用兩次實錯證明）。
被條件擋掉的那些節點，它們的詳細頁就又沒有入口了 —— 而這一節要修的正是「沒有入口」。

**這一版還沒做，因為視覺還沒畫**（`CLAUDE.md` 的 Figma 先行）。
有列的版面上擺哪裡都有代價：擺最上面會插進「出門前核包」的掃視路徑，擺最下面要滑過
整份清單。而空狀態那一版**必須**一起畫 —— §4.2d 的空狀態目前佔滿整個版面，
而那正是缺口二唯一會出現的地方。

**還有一項代價要在那一支裡一起回答：它與 §4.4c 那一列合起來會成為一個兩點循環。**
詳細頁 → 盤點頁 → 詳細頁 → 盤點頁，每一步都往導覽堆疊推一層。返回鍵（§4.0）**確實**會
照原路退回去，問題不在那裡 —— 在於堆疊會被同一組、外觀幾乎分不出來的頁面無限填滿：
要退回首頁得一層按一次，而使用者看不出自己現在在第幾層。

用語傾向 `<名稱>的檔案`，沿用 §4.4 對詳細頁的說法（「一個 Node 的完整檔案」），
但那同樣要先在 Figma 上成立才算數。

### 4.4b 查詢語意

> 編號跳過 `b` 不是漏寫：這一節講的是查詢，不是詳細頁，當初編在 4.4 底下是筆誤，
> 但 `§4.4b` 已經被 SPEC 與程式碼引用十幾處，改編號的代價大於這點不整齊。
> 詳細頁本身的子節是 §4.4a、§4.4c–§4.4f。

首頁與 sheet 需要三種查詢，語意在這裡定死，避免各畫面各自解讀。

**首頁分組**
- 「地點」= 所有根節點（`parent == nil`），依名稱排序
- 「釘選」= 所有 `isPinned` 的節點，依名稱排序
- 一個節點同時是根節點又被釘選時，**兩組都出現**。釘選是使用者主動的置頂，
  不該因為它剛好是根節點就消失

**被移到頂層的東西會出現在「地點」裡，這是刻意的。**

§4.3a 的「不放在任何容器裡」把 `parent` 設成 `nil`，那個東西就變成根節點，於是雨衣會
跟家、書房、公司並排列在「地點」底下，顯示「0 件」。看起來很怪，但另外兩個選項更糟：

- **把它從首頁濾掉** —— 沒有容器裝它，它就不會出現在任何盤點頁上（除非它剛好有歸屬地，
  那時還看得到一列 `✗`）。歸屬地是選填的，所以濾掉等於讓一部分東西只剩搜尋找得到。
  使用者剛剛才說「它不在包裡了」，下一秒它就從畫面上消失，這比排版怪嚴重得多
- **改成「只有帶子節點的根節點才算地點」** —— §2.1 明確拒絕區分容器與物件（「筆袋」在裝
  第一支筆之前不能長得不一樣）。為了首頁的排版把那個區分偷渡回來，會讓新建的空容器
  也一起從首頁消失

所以現階段接受它，而且**這個接受在詳細頁做出來之後重新檢查過一次，結論不變。**

本節原本寫著「真正的解法是物件詳細頁（§4.4）—— 有了它，頂層的東西就有別的入口可以抵達」，
並要求在詳細頁做出來之前不要動這裡。詳細頁做出來了（§4.4a），而那句話**把兩件事弄混了**：

**詳細頁確實讓搜尋那條路變好了。** 它做出來之前，搜尋結果通往的是盤點頁，一個頂層葉節點
在那裡只會顯示「還沒有東西」；現在通往詳細頁（§4.4c），那裡真的回答得了「它在哪」——
目前位置寫著「不在任何容器裡」，時間軸講得出它是怎麼變成這樣的。

**但入口的數量一個都沒有增加。** 講清楚前提免得被讀反：頂層的東西今天**有**首頁這個
入口，「地點」列的就是所有根節點 —— 這一節在問的正是「可不可以把它拿掉」。而**拿掉之後**，
找得到它的方式仍然只有搜尋（或它剛好填了歸屬地時，歸屬地那一頁上的那一列 `✗`）。
詳細頁是個目的地，不是入口 —— 它改善的是「走到之後看到什麼」，不是「有幾條路走得到」。
原句押的是後者，而事實只發生了前者。

所以否決選項一的第一個理由（「濾掉等於讓一部分東西只剩搜尋找得到」）原封不動成立。
**而那一條本來就不是主要理由** —— 主要理由是後面那句：「使用者剛剛才說『它不在包裡了』，
下一秒它就從畫面上消失」。那句話與詳細頁做不做得出來完全無關，做得再好也不會改變
「東西從首頁消失」這件事本身。

選項二則是 §4.4c 後來用兩次實錯證明過的那個形狀：任何以「有沒有子節點」「列不列得出
東西」為條件的濾法，都會有一類節點從首頁消失。

**但重新檢查翻出了另一件事，而它不是「哪些根節點算地點」—— 見 §4.4f。**

**下一次什麼情況才該重新問這一節：** 不是「某個畫面做出來了」，也不是「多了一條抵達
路徑」，而是**首頁上出現一個地方，讓剛被移到頂層的東西即使不列在「地點」底下也仍然
看得見**（例如自成一組的「不在任何容器裡」）。

理由就是上面那條：主要的否決理由是「使用者剛說完它不在包裡了，下一秒它就從畫面上消失」。
只要那句話還成立，多幾條抵達路徑都不會改變答案 —— 拿路徑數量當觸發條件，只會讓未來的人
重新論證一整輪，然後落回同一個結論。**觸發條件要對準主要理由。**

順帶記下一個一定會被踩的陷阱：§4.4f 的修法會讓「首頁『地點』→ 盤點頁 → 詳細頁」變成
一條新的路，看起來像是「多了一條不靠搜尋的路」—— 但那條路的第一步就是要被濾掉的那一列，
濾掉之後它跟著消失。**拿一條途經該列的路徑去論證該列可以拿掉，是循環論證。**

這一節上一版把觸發條件下錯了：它押在一個畫面存不存在。這一版差一點犯了同一個錯的另一個
版本 —— 押在路徑數量，而那正是它自己上一段才剛說過「不是主要理由」的那一條。

**搜尋**
- 比對**名稱與備註**，不分大小寫。備註要納入，是因為使用者常把型號、顏色寫在備註裡
- 結果依 `updatedAt` 由新到舊排序 —— 剛動過的東西最可能是你正在找的
- 空字串或全空白回傳空結果，不是回傳全部

**最近使用的容器**（「它在哪？」sheet 的第一組選項）
- 取自 `MoveEvent` 的 `to`，依 `at` 由新到舊，去除重複，只留仍存在的容器
- 排除該物件目前所在的容器 —— 把東西移到它已經在的地方不是一次移動。
  從盤點頁開 sheet 時這個容器就是正在檢視的那一頁（§4.2e 只有 `✓` 與 `○` 會開 sheet，
  而那兩種狀態的前提都是「人在這裡」），但排除的依據是 `parent`，不是畫面
- §4.3b 還會再排除自己與自己的子孫。那是循環防呆，不屬於這條查詢的語意

### 4.5 新增物件

```
新增物件

名稱   [ 頭燈          ]   ← 唯一必填
位置   [ 登山包     更改 ]
歸屬地 [ 同位置     更改 ]   ← 預設跟著位置走

[      完成建檔       ]
[      再新增一件      ]
```

對照 Figma `Screens — Light / Item — Add`。導覽列是 Inline 置中標題，不是大標題 ——
這一頁是一次性的任務，標題只需要說明「你正在做什麼」，不是這一頁的主角。

#### 4.5a 欄位

| 欄位 | 必填 | 預設 |
|---|---|---|
| 名稱 | 是 | 空的，或由入口帶入（§4.5b） |
| 位置 | 否 | 由入口決定（§4.5b） |
| 歸屬地 | 否 | 「同位置」—— 跟著位置走，直到使用者手動改過 |

名稱只有空白字元一樣算沒填。沒填的時候兩顆按鈕都不可按 —— 名稱是這個 app 的識別主鍵
（§2.1），一筆沒有名稱的資料在任何畫面上都認不出來，建了等於製造垃圾。

**不可按是這一頁的初始狀態，不是例外狀態。** 三個入口有兩個是空著名稱進來的，所以
使用者看到這一頁的第一眼就是那個樣子，對照 Figma `Item — Add — Empty`。名稱欄這時顯示
提示字「例如：頭燈」，走 `text/tertiary`，與搜尋列的 placeholder 是同一個處理。

按鈕的不可按樣式見 Figma `Button` 的 `State=Disabled`：底走 `bg/field`、字走 `text/tertiary`，
兩個都是既有 token，沒有為這個狀態新增專用色。

**「同位置」不是把值複製過去，是一種持續的狀態。**
使用者還沒碰過歸屬地時，改位置，歸屬地跟著改。一旦他自己選過**別的**歸屬地，兩者就脫鉤，
之後再改位置也不會覆蓋掉他的選擇。

**打開選擇器又挑了同一個值，不算選過。** 那一下在畫面上什麼都沒改變，脫鉤卻已經發生 ——
接著改位置就會建出一筆立刻被算成缺件的資料，而使用者從頭到尾沒有說過任何東西放錯地方。
脫鉤是個看不見的狀態，只有真的改變了值才值得付出這個代價。

理由：兩個欄位在絕大多數情況下是同一個答案（東西就放在它該在的地方），所以預設要連動；
但「先設好歸屬地、再改位置」正是「這件東西現在暫時放在別的地方」的建檔情境，那時把
使用者剛選的歸屬地悄悄蓋掉，會讓他建出一筆與他所想相反的資料。

**為什麼沒有備註欄：**
目標是「8 件裝備 60 秒建完」。自由文字欄會誘發打字，而它對「現在這件東西叫什麼、在哪」
沒有貢獻。備註仍然存在於模型上，也仍然會被搜尋比對到（§4.4b），從物件詳細頁補即可。

**為什麼照片選填：**
目標同上。強制拍照會讓每件變成 15–30 秒，建到第 5 件就放棄。
照片是輔助回想，不是識別主鍵 —— 名稱才是。

**照片欄在 `PhotoStore` 做出來之前不出現在這一頁上。**
一列寫著「選填，之後補也可以」卻按了沒反應，比沒有那一列更糟：它承諾了一個不存在的功能。
對照 Figma `Item — Add`（現行，無照片欄）與 `Item — Add — With Photo`（`PhotoStore` 完成後切回去）。

#### 4.5b 三個入口各自帶進來什麼

這一頁只有三個入口，全部來自空狀態的動作。**沒有 GPS 的這一版，預填的依據是「你從哪裡來」**，
那比 GPS 更確定 —— 使用者剛剛才在那個容器的頁面上。

| 入口 | 名稱 | 位置 |
|---|---|---|
| 盤點頁「加入第一件」（§4.2d 空容器） | 空的 | 那個容器 |
| 首頁「建立第一個空間」（§4.1a 空） | 空的 | 不放在任何容器裡 |
| 搜尋無結果「建立「X」」（§4.1a 搜尋） | `X` | 最近用過的第一個容器；沒有就留空 |

**為什麼首頁的空狀態預設是頂層：**
那個動作的字面是「建立第一個空間」。空間就是根節點（§4.4b 的「地點」），一個庫還空著的時候
也沒有別的容器可以放。

**為什麼搜尋無結果要猜「最近用過的第一個」：**
沒有 GPS 的情況下，「你剛剛才放東西進去的那個容器」是手上最好的猜測，連續建檔時尤其準。
猜錯的代價是一次「更改」，猜對省下的是每一件都要選一次位置。GPS 做出來之後，這條規則
直接被 §5 的「人在家 → 從家底下最近用過的挑」取代。

#### 4.5c 兩個按鈕

- **完成建檔** —— 建立節點、寫一筆 `MoveEvent`（`from` 為 `nil` 代表建檔，見 §2.2），
  然後離開這一頁
- **再新增一件** —— 一樣建立並寫歷史，但**留在這一頁**，只清空名稱，位置與歸屬地原封不動

**為什麼「再新增一件」不把整支表單重置：**
它服務的是「把登山包裡八件裝備一次建完」。那個情境裡位置與歸屬地從頭到尾是同一個答案，
每一件都要重選一次，等於把這個按鈕存在的理由抵銷掉。

兩個按鈕做的事只差在建完之後留不留在這一頁，所以**驗證與寫入的規則完全一樣** ——
名稱沒填時兩顆都不可按。

**建檔沒有存檔成功就當作沒建過：把剛插入的節點與那筆歷史一起收回，並留在這一頁。**

這與 §4.2e 的移動處理方式不同，差別是有理由的。移動改的是一個已經存在的節點，把它改回去
會變成第三種與磁碟、與畫面都不符的說法；建檔則是憑空多一筆，收回之後記憶體與磁碟又
完全一致，等於那個動作沒發生過。而如果不收回，這一頁會**表演出一次成功**——畫面退回去、
或名稱欄清空讓你接著建下一件——使用者於是連續建了八件，八件全部沒有落地。

存檔失敗仍然沒有東西告訴使用者（與 §4.2e 是同一個缺口，要等錯誤提示的設計）。
但「留在原地、什麼都沒發生」至少不會騙人。

#### 4.5d 位置與歸屬地怎麼選

按「更改」彈出的就是「它在哪？」sheet（§4.3），只換標題：位置是「放在哪？」、
歸屬地是「歸屬在哪？」。

**為什麼不另做一支簡化的選單：**
要回答的是同一個問題（從所有節點裡挑一個地方），選項的組成、排序、搜尋、
「最近用過」的語意也完全一樣。另做一支等於把同一套規則寫兩遍，然後讓它們各自漂移。

差別只有一項：**還不存在的東西沒有自己與子孫要排除**（§4.3b 的前兩條），
也沒有「目前的 parent」。所以排除規則的輸入是可選的，沒有節點時就一條都不排除。
「不放在任何容器裡」那一列仍然要有 —— 它是首頁那個入口的預設值。

## 5. GPS 的角色

權限：**When-In-Use only**。

- 建檔 / 移動時自動抓一次座標，寫進 `MoveEvent`，反向地理編碼成地名
- **主要價值是降低輸入摩擦**：人在家 → 新增物件時預設容器就從「家」底下最近用過的挑
- 次要價值：表達「東西臨時放在某個非容器的地方」（掉在某咖啡廳）

**不做**背景定位、地理圍籬、Always 權限。

## 6. 明確不做（MVP 非目標）

| 項目 | 原因 |
|---|---|
| 提醒 / 通知（離家提醒、定期盤點） | 提醒的前提是資料新鮮。資料是否會被維護還沒驗證，不新鮮的提醒只是噪音。且要 Always 定位 + 背景執行 + 通知三層權限。 |
| CloudKit 多裝置同步 | 模型已相容，開關留著。MVP 不處理登入態、衝突、配額。 |
| 分享 / 家庭共用 | 需要帳號系統與後端。 |
| 條碼 / QR / NFC 標籤 | 服務規模只有 20–80 件，貼標的成本高於效益。 |
| 標籤 / 多重分類 | 見 §2.1。 |
| 數量欄位 | 見 §2.1。 |
| 批次匯入 / CSV / OCR | 見 §1 規模假設。 |

## 7. 刪除語意

刪除一個有子節點的 Node → **子節點上移到祖父層**（`deleteRule: .nullify` + 手動 reparent）。

絕不連帶刪除。沒有雲端備份的情況下，一次誤觸不該蒸發幾十筆資料。

**被上移的子節點各寫一筆 `MoveEvent`。**

理由：§2.2 存歷史是為了「回想最後一次在哪」與「誤操作可還原」。不寫的話，筆的歷史
最後一筆停在「移入筆袋」，但筆袋已經不存在、筆現在在上班包，中間那一步是斷的 ——
而刪錯容器正是最需要被追溯的誤操作。

歷史記錄的是**東西在哪**，不是**誰移動的**，所以系統造成的位置變更同樣要入帳。

被刪節點若是別人的歸屬地，那些 `home` 一律清成 `nil`，不留懸空參照。歸屬地的變更
不寫 `MoveEvent` —— 那是「應該在哪」的變更，不是位置變更。

## 8. 工程設定

### 專案結構（XcodeGen）

```
where-are-you/
  project.yml                    ← 進版控
  docs/SPEC.md
  Sources/
    App/         WhereAreYouApp.swift
    Models/      Node.swift, MoveEvent.swift
    Logic/       TreeQueries.swift（遞迴 / 缺件 / 循環防呆）
    Views/       HomeView, ContainerView, ItemDetailView, AddItemView, WhereIsItSheet
    Services/    LocationService, PhotoStore
  Tests/
  .gitignore                     ← 排除 *.xcodeproj
```

`.xcodeproj` **不進版控**，避免 pbxproj 衝突；`xcodegen && xcodebuild build` 即可驗證。

### 資料庫開不起來時

啟動時若 `ModelContainer` 建不出來（最常見的原因是裝置上留著舊 schema 寫出來的 store），
**把舊檔移到旁邊、用新的 store 再開一次**，不是直接當掉。移開時連同 `-shm` / `-wal`
一起搬，檔名加上時間戳。

**絕不刪除舊檔。** 理由與 §7 的刪除語意同一條：沒有雲端備份的情況下，一次啟動失敗
不該蒸發使用者的全部資料。移開之後資料還在檔案系統上，要撈得回來。

**為什麼不是直接當掉：**
schema 還在長的階段，這個情況是常態而不是例外。當掉的結果是一個打不開、也看不出
為什麼打不開的 app —— 使用者唯一能做的是砍掉重裝，那等於強制刪資料，比移開更糟。

**三個檔是一組，搬一半等於沒搬。** 只要有任何一個搬不動就停手、不要接著開新 store ——
新的 store 會生在殘留的 `-wal` 旁邊，然後把舊的未提交交易重播進一個全新的資料庫。
那比當掉還糟：資料看起來在，但內容是兩個世代混出來的。

移開之後仍然開不起來，才是真的壞了，那時才當掉。當掉時**原始錯誤與第二次的錯誤都要印**：
說明「為什麼壞掉」的是原始錯誤，第二次那個講的是一個全新的空 store 也開不起來，
通常只是同一個環境問題的回音。只印後者會把最有用的線索丟掉。

### 測試策略

只測邏輯層，用 Swift Testing + in-memory `ModelContainer`：

- 遞迴計數包含孫節點
- 缺件計算：離開子樹才算缺（含 §3.2 的橡皮擦反例）
- 外來件計算
- 移動到自己的子孫會被拒絕
- 刪除容器後子節點上移到祖父

不寫 UI Test — 對單人 MVP 太脆、太慢。

## 9. 視覺方向（v2）

> v1 曾走「iOS 原生為骨」，做出來太像系統設定 App，已作廢。
> 現行方向參考 Uber / Untitled UI / MiLi MiTag 的簡約語言。

**白底、Inter、零卡片、零分隔線、零 chevron。**

層級完全由**字重、尺寸與間距節奏**撐起，不靠灰底分組、不靠框線。
綠色只出現在三個地方：主按鈕、「在」狀態記號、移動歷史的當前節點。

| 決策 | v1（作廢） | v2（現行） |
|---|---|---|
| 底色 | 灰底 `#F2F2F7` + 白卡片 | 整面純白，無卡片 |
| 分隔 | 每列 hairline | 零分隔線，靠 56pt 列高與群組間距 |
| 字型 | SF Pro 全域 | Inter 走拉丁與數字，中文用系統黑體 |
| 列高 | 44pt | 56pt |
| chevron | 每列都有 | 全部移除，整列即觸控目標 |
| 群組標題 | iOS 區段標題 | 12/16 Semi Bold + 1.6 字距 |
| 表單 | 左標籤右值同列 | 標籤在上、值在下，底線一條 hairline |
| 歷史 | 條列 + 分隔線 | 左側時間軸，當前節點用強調色 |

### 不使用 emoji（硬規則）

介面、程式碼、文件一律不用 emoji。容器圖示、狀態指示、按鈕圖示全部走**向量字符**
（`Icon/Glyph` 元件，24×24 線性、可 tint、可綁 token）。

理由：emoji 無法 tint、深色模式下對比不可控、跨系統版本外觀會變、無障礙朗讀結果雜亂，
而且尺寸與線寬跟 SF Symbols 對不齊。使用者自訂容器的識別改用「圖示 + 強調色」，不用 emoji。

### Token（v2 實際值）

| Token | Light | Dark | 對比 |
|---|---|---|---|
| `bg/grouped`（畫面地） | `#FFFFFF` | `#0B0C0D` | — |
| `bg/field` | `#F3F4F5` | `#17191B` | — |
| `bg/elevated`（sheet） | `#FFFFFF` | `#16191A` | — |
| `text/primary` | `#111315` | `#F2F4F4` | 18.6 / 17.7 |

| `text/tertiary` | `#6F757B` | `#8A9198` | 4.66 / 6.14 |
| `text/danger` | `#C9251C` | `#FF6F63` | 4.84 / 6.38 |
| `border/separator` | `#EDEEEF` | `#212426` | 1.16 / 1.25 |
| `accent` · `state/ok` | `#2F6F4E` | `#4CAF7D` | 5.99 / 7.21 |

字級：Inter — Large Title 30/35 Bold · Title 2 21/27 Bold · Title 3 19/25 Semi Bold ·
Headline 17/23 Semi Bold · Body 17/23 Medium · Subhead 14/20 · Footnote 13/18 ·
Footnote Emphasis 13/18 Semi Bold（徽章專用）· Caption 12/16 Semi Bold +1.6 字距
（群組標籤與表單標籤專用）。

**為什麼徽章要單獨一個字級而不是共用現有的：**
`缺 2` 這種徽章要在一行掃視裡被抓到，Regular 的 Footnote 抓不住；Caption 的 +1.6 字距
是為了讓孤立的群組標籤撐開，用在兩三個字的徽章上會把膠囊撐得比內容還寬。
差一個字重就多一個 token，是因為 token 表是唯一能被機械對照的東西 —— 讓某個地方
「就直接寫 semibold」等於在這份契約上開一個洞。

**層級不靠亮度差，靠尺寸與字距。** `text/tertiary` 與 `text/secondary` 亮度接近是刻意的 ——
在零分隔線的版面裡，群組標籤是唯一的分組訊號，淡到看不清等於沒有分組。

**唯一刻意不合規的項目**：`border/separator` 對比 1.16。它是欄位底線與時間軸的裝飾性邊界，
不承載狀態辨識（標籤與值本身承載），拉高會讓畫面重新變得吵。這是有意識的取捨。
