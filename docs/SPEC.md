# Where Are You — MVP 規格

> 本文件是 2026-08-09 設計訪談的產出，記錄每一項決策與**為什麼**排除其他選項。
> 實作若要偏離本文件，先回來改這裡。

App 名稱：**Where Are You**
Bundle ID：`com.chienchuanw.whereareyou`
平台：iOS 18+ / SwiftUI / SwiftData / Swift 6.3 / Xcode 26.6

---

## 1. 產品定位

幫使用者回答兩個問題，而且要在**三秒內**：

1. 「這東西最後一次在哪？」 — 被動查詢
2. 「包包裡該有的東西都在嗎？」 — 出門前核對

**服務規模假設：一個使用者 20–80 件高價值物品**（會搞丟的、很重要的、出門必帶的）。
不是全屋資產盤點工具。因此不做批次匯入、條碼掃描、OCR、CSV。

## 2. 資料模型

### 2.1 Node — 唯一的實體

**一切都是 Node。** 沒有「容器」與「物件」之分：任何 Node 都能裝下另一個 Node。

```swift
@Model final class Node {
    var id: UUID = UUID()
    var name: String = ""              // 必填，識別主鍵
    var note: String = ""              // 自由備註（取代「分類說明」）
    var parent: Node?                  // 目前實際在哪
    var home: Node?                    // 歸屬地：本來應該在哪（選填）
    var isPinned: Bool = false         // 是否釘在首頁
    var photoFilename: String?         // 檔案在 Documents/，DB 只存檔名
    var createdAt: Date = Date()
    var updatedAt: Date = Date()
}
```

**為什麼統一遞迴而不是「空間 → 容器 → 物件」三層：**
容器自己會移動。登山包被帶去公司時，裡面的充電線位置必須自動跟著走。
三層固定模型無法表達「包中包」、也無法讓包包自己擁有位置歷史。

**為什麼不區分 isContainer：**
「筆袋」到底算容器還是物品？這個決定對使用者沒有意義卻必須做。
改成：**有子節點的 Node 在 UI 上就是可展開的容器**，建檔時少填一欄。

**為什麼沒有 tags / category：**
使用者原本說的「分類」就是收納空間本身。容器階層即分類。
跨容器查詢（「所有充電線在哪」）靠名稱搜尋解決，不值得為此多一張關聯表 + 一套標籤管理 UI。

**為什麼沒有 quantity：**
數量與位置模型直接衝突 — 三條充電線分別在包包、車上、書房，`quantity = 3` 要掛在哪個節點？
20–80 件高價值物品本來就幾乎都是單件。需要區分就用名稱（「充電線(USB-C 短)」）。

### 2.2 MoveEvent — 移動歷史

```swift
@Model final class MoveEvent {
    var id: UUID = UUID()
    var node: Node?
    var from: Node?                    // nil = 建檔
    var to: Node?
    var at: Date = Date()
    var latitude: Double?              // 當下 GPS（選填）
    var longitude: Double?
    var placemark: String?             // 反向地理編碼後的地名，如「信義區」
    var photoFilename: String?         // 現場照（選填）
}
```

**為什麼存完整歷史而不是只存 `lastMovedAt`：**
「回想最後一次在哪」常常需要往回看不只一步。而且誤操作可還原、日後要做「常去哪」分析不必重建資料。
寫入成本極低。

**歷史同時存名稱快照，不只存參照。**

`MoveEvent` 除了 `node` / `from` / `to` 三個關聯，另存 `nodeName` / `fromName` / `toName`
三個字串。空字串在 `fromName` 代表建檔、在 `toName` 代表移到頂層。

理由有兩個，第二個是硬性的：

1. **歷史是只增不改的紀錄，不該因為容器被刪就掉資訊。** 「書房抽屜 ← 登山包」在登山包
   被刪之後仍然要讀得出來，否則 §4.4 的時間軸會出現無法解讀的空白。刪除容器正是最
   需要回溯的情境，卻剛好是資訊被抹掉的情境，這說不通。
2. **不存快照的話，程式會當掉。** 三個關聯必須在 `Node` 上宣告對應的 inverse 並設
   `deleteRule: .nullify`，否則節點被刪除並存檔後再讀 `event.to`，SwiftData 會拋
   `This model instance was invalidated because its backing data could no longer be
   found in the store`。inverse 補上之後參照會安全地變成 `nil` —— 但那也代表參照本身
   靠不住，所以顯示一律以名稱快照為準，關聯只用於「該節點還在時可以點進去」。

快照凍結在事件寫入的當下，**之後不再同步**。所以把容器改名之後，舊的歷史條目會繼續
顯示舊名稱。這是刻意的：歷史講的是「當時那個東西叫什麼、在哪」，不是「它現在叫什麼」。
實務上改名比刪除常見得多，這個後果要先講清楚，免得被當成 bug。

### 2.3 CloudKit 相容性（重要）

MVP **只存本機、不開同步**，但模型從第一天就遵守 CloudKit 限制：

- 所有純量屬性都有預設值
- 所有關聯都是 optional
- 不使用 `@Attribute(.unique)`
- 照片存檔案系統，DB 只存檔名

之後只要加 `.cloudKitDatabase(.automatic)` 就能開多裝置同步，不需要痛苦的 schema 遷移。

## 3. 核心運算語意

以下四項是最容易寫錯的地方，全部要有單元測試。

### 3.1 遞迴計數

容器 C 顯示的「N 件」= `subtree(C)` 中**所有子孫**的數量（不含 C 自己）。

### 3.2 缺件（missing）

```
missing(C) = { n : home(n) ∈ subtree(C) 且 parent-chain(n) ∉ subtree(C) }
```

**只有東西離開整棵子樹才算「缺」。**

範例：`上班包 → 筆袋 → 鑑子筆`，橡皮擦 `home = 筆袋` 但目前直接躺在上班包裡 →
**不算缺**，因為東西還在包裡，出門情境不該為此警示。

**為什麼不用 `now ≠ home`：**
那會讓「東西在包裡只是沒放回筆袋」變成假警報，徽章很快就會被使用者忽略。

### 3.3 外來件（foreign）

```
foreign(C) = { n : parent-chain(n) ∈ subtree(C) 且 home(n) ≠ nil 且 home(n) ∉ subtree(C) }
```

顯示為 `○`，不計入「缺 N」。`home == nil` 的物件永遠不算缺、也不算外來。

### 3.4 循環防呆

`parent` 不得設為自己或自己的任一子孫。移動前必須檢查，違反則拒絕並提示。

## 4. 畫面與流程

### 4.0 導覽

首頁是根，其他畫面都是從它推進去的。被推進去的畫面**在大標題上方帶一個返回鍵**
（Figma `NavBar` 的 `Back` 屬性），首頁沒有。

**為什麼不用 iOS 內建的返回鍵：**
v2 的大標題是自繪的（§9），畫面沒有系統導覽列可以掛返回鍵。留著系統導覽列會多出一條
它自己的底線與高度，正好是 v2 要拿掉的東西。

**為什麼不改用 Inline 導覽列（它本來就有返回鍵）：**
盤點頁的標題是容器名稱，是這一頁最重要的一行字。降成 17pt 的 inline 標題會讓
「我現在在哪個包裡」變成畫面上最不明顯的資訊，而那正是使用者點進來的理由。

**為什麼不只靠邊緣滑動返回：**
可用但不可發現。返回是這個 app 除了點列以外唯一的導覽動作，不該藏在手勢裡。

### 4.1 首頁

```
我的東西

搜尋物件

釘選
登山包                8 件   缺 2
上班包                6 件   缺 1

地點
家                   42 件
書房                  18 件
公司                   5 件
車                     5 件
```

無卡片、無分隔線、無 chevron，也**不用 emoji** —— 容器的識別靠名稱與強調色，
不靠圖示。分群只由群組標籤與間距造成。對照 Figma `Screens — Light / Home`。

首頁 = **所有根節點（`parent == nil`）+ 所有 `isPinned` 的節點**。

**為什麼需要 isPinned：**
登山包的 parent 通常是「家/儲藏室」，若首頁只列根節點，最高頻的動作（出門前核包）反而藏得最深。
一個 Bool 解決。

搜尋列固定在頂部，同時服務「找東西」情境。**唯一的例外是一件東西都還沒有的時候** ——
那時整支搜尋列不出現，見 §4.1a。

#### 4.1a 首頁的三個狀態

| 狀態 | 條件 | 畫面 |
|---|---|---|
| 一般 | 有節點，且搜尋列是空的 | 搜尋列 + 釘選 / 地點兩組 |
| 空 | 一個節點都沒有 | 不放搜尋列，改放「還沒有任何收納空間」，動作是建立第一個空間 |
| 搜尋 | 搜尋列有字 | 兩組收起來，改列搜尋結果；沒有結果就放「找不到「X」」，動作是直接建立「X」 |

對照 Figma `Home — Empty` 與 `Search — No Results`。

**為什麼空的時候不放搜尋列：**
搜尋列在這支 app 裡是「找東西」的入口，而不是裝飾。一個節點都沒有時它搜不到任何東西，
擺著只是要使用者先讀懂一個沒有作用的控制項，再往下找到真正該做的那件事。
空狀態只該有一個動作，那個動作就是建第一個空間。

**為什麼搜尋時把釘選與地點兩組收起來，而不是把結果接在下面：**
搜尋是「我現在只想看這個」的動作。把結果疊在原本的兩組下面，使用者得先滑過一整頁
他此刻不關心的東西。這也是為什麼找不到時要直接給出建檔動作 —— 搜尋落空的下一步
幾乎一定是「那就現在建一筆」。

### 4.2 容器盤點頁（主要更新入口）

```
登山包
5 件 · 缺 1 · 8 月 9 日更新

✓ 頭燈
✓ 水壺
✗ 雨衣
  在陽台
○ 充電線
  歸屬在書房抽屜
✓ 急救包
```

對照 Figma `Screens — Light / Container — Inventory`。

**點任一列的狀態圖示即切換「在 / 不在」**，切成「不在」時彈出 sheet 問「它在哪？」。

**為什麼以盤點為主要更新入口而非單筆編輯：**
使用者不會在搬動物品的當下開 app。他是在「出門前核包」時才發現資料要修。
把更新做在他自然會來的那個畫面，而不是要他事後回想著去搜尋每一件。

單筆編輯仍可從詳細頁進行，但不為它做優化。

#### 4.2a 這一頁到底列出哪些東西

列表 = **直接子節點 ∪ `missing(C)`**（`missing` 的定義見 §3.2）。

缺件必須列出來，即使它已經不在這個容器裡 —— 否則 `✗` 這個狀態根本沒有列可以掛。
「雨衣的歸屬地是登山包但人在陽台」正是出門前最需要看到的那一行，把它藏起來等於
把整頁最有價值的資訊刪掉。

**只列直接子節點，不遞迴展開。** 標頭的「N 件」是遞迴的（§3.1），但列表不是。
理由：包中包要能被點進去自己的盤點頁，攤平會讓「筆袋」這一層消失，使用者也就無法
在筆袋自己的頁面上核對筆袋。標頭回答「總共帶了多少」，列表回答「這一層有什麼」。

一個節點同時是子節點又是缺件在定義上不可能（缺件的前提是 parent-chain 不在子樹裡），
所以聯集不需要去重規則。

#### 4.2b 每一列的狀態與副標

| 狀態 | 判定 | 記號 | 副標 |
|---|---|---|---|
| 在 | 人在這裡，且 `home` 是 `nil` 或落在這棵子樹裡 | `✓` | 無 |
| 缺 | 落在 `missing(C)` 裡 | `✗` | 「在 <目前所在的容器名>」，頂層則寫「不在任何容器裡」 |
| 外來 | 落在 `foreign(C)` 裡 | `○` | 「歸屬在 <home 的名稱>」 |

`home == nil` 的東西顯示為 `✓` 而不是另一種狀態。它既不算缺也不算外來（§3.3），
再多一種記號只是要使用者去理解一個對他沒有意義的區別。

**為什麼副標不寫成 `home=登山包` 這種鍵值格式：**
盤點是掃視動作，不是閱讀動作。`✓` 已經說完「該在這、也在這」，再補一句 `home=登山包`
是純冗餘；而 `✗` 與 `○` 各自缺的那一塊資訊不同 —— 前者要知道「那它跑去哪了」，
後者要知道「那它該回哪」。兩種狀態各補各的那一句，比統一格式更省眼力。

#### 4.2c 排序

單一列表，依名稱排序（`localizedStandardCompare`），不依狀態分組。

**為什麼不把缺件排在最前面：**
盤點是一邊核對一邊切換狀態的過程。依狀態排序會讓使用者每按一次記號、那一列就跳走，
核到一半找不到剛才看到哪裡。缺件的顯眼程度由紅色記號承擔，不需要再靠位置強調。

#### 4.2d 標頭行

`<遞迴件數> 件 · 缺 <缺件數> · <最後更新日期>更新`

- 缺件數為 0 時整段「· 缺 N」不出現，不寫「缺 0」
- 日期取這個容器與其子孫之中最新的 `updatedAt`，格式為當地的「M 月 d 日」
- 空容器（無子節點且無缺件）改顯示「還沒有東西」，見 Figma `Container — Empty`

**為什麼要有最後更新日期：**
盤點資料的價值完全取決於新鮮度。一份三個月沒動過的清單，`✓` 代表的是「三個月前在」，
不講出來的話使用者會把它讀成「現在在」，那比沒有資料更危險。

### 4.3 「它在哪？」sheet

選新位置，選項排序：最近使用的容器 → GPS 推測的當前地點底下的容器 → 完整樹狀瀏覽 → 搜尋。

### 4.4 物件詳細頁

名稱、備註、照片、目前位置、歸屬地、以及**完整移動歷史時間軸**：

```
08/09 20:20   書房抽屜 ← 登山包    · 信義區
07/22 09:14   登山包 ← 保險箱      · 大安區
06/01 11:03   建檔於保險箱
```

### 4.4b 查詢語意

首頁與 sheet 需要三種查詢，語意在這裡定死，避免各畫面各自解讀。

**首頁分組**
- 「地點」= 所有根節點（`parent == nil`），依名稱排序
- 「釘選」= 所有 `isPinned` 的節點，依名稱排序
- 一個節點同時是根節點又被釘選時，**兩組都出現**。釘選是使用者主動的置頂，
  不該因為它剛好是根節點就消失

**搜尋**
- 比對**名稱與備註**，不分大小寫。備註要納入，是因為使用者常把型號、顏色寫在備註裡
- 結果依 `updatedAt` 由新到舊排序 —— 剛動過的東西最可能是你正在找的
- 空字串或全空白回傳空結果，不是回傳全部

**最近使用的容器**（「它在哪？」sheet 的第一組選項）
- 取自 `MoveEvent` 的 `to`，依 `at` 由新到舊，去除重複，只留仍存在的容器
- 排除目前正在檢視的那個容器 —— 把東西移到它已經在的地方沒有意義

### 4.5 新增物件

```
名稱  [ 頭燈           ]   ← 唯一必填
位置  [ 登山包      ▾ ]   ← GPS 推測預設值
歸屬  [ 同上         ▾ ]   ← 預設等於位置
照片  [ ⊕ 之後再拍     ]
備註  [                ]
```

**為什麼照片選填：**
目標是「8 件裝備 60 秒建完」。強制拍照會讓每件變成 15–30 秒，建到第 5 件就放棄。
照片是輔助回想，不是識別主鍵 — 名稱才是。

## 5. GPS 的角色

權限：**When-In-Use only**。

- 建檔 / 移動時自動抓一次座標，寫進 `MoveEvent`，反向地理編碼成地名
- **主要價值是降低輸入摩擦**：人在家 → 新增物件時預設容器就從「家」底下最近用過的挑
- 次要價值：表達「東西臨時放在某個非容器的地方」（掉在某咖啡廳）

**不做**背景定位、地理圍籬、Always 權限。

## 6. 明確不做（MVP 非目標）

| 項目 | 原因 |
|---|---|
| 提醒 / 通知（離家提醒、定期盤點） | 提醒的前提是資料新鮮。資料是否會被維護還沒驗證，不新鮮的提醒只是噪音。且要 Always 定位 + 背景執行 + 通知三層權限。 |
| CloudKit 多裝置同步 | 模型已相容，開關留著。MVP 不處理登入態、衝突、配額。 |
| 分享 / 家庭共用 | 需要帳號系統與後端。 |
| 條碼 / QR / NFC 標籤 | 服務規模只有 20–80 件，貼標的成本高於效益。 |
| 標籤 / 多重分類 | 見 §2.1。 |
| 數量欄位 | 見 §2.1。 |
| 批次匯入 / CSV / OCR | 見 §1 規模假設。 |

## 7. 刪除語意

刪除一個有子節點的 Node → **子節點上移到祖父層**（`deleteRule: .nullify` + 手動 reparent）。

絕不連帶刪除。沒有雲端備份的情況下，一次誤觸不該蒸發幾十筆資料。

**被上移的子節點各寫一筆 `MoveEvent`。**

理由：§2.2 存歷史是為了「回想最後一次在哪」與「誤操作可還原」。不寫的話，筆的歷史
最後一筆停在「移入筆袋」，但筆袋已經不存在、筆現在在上班包，中間那一步是斷的 ——
而刪錯容器正是最需要被追溯的誤操作。

歷史記錄的是**東西在哪**，不是**誰移動的**，所以系統造成的位置變更同樣要入帳。

被刪節點若是別人的歸屬地，那些 `home` 一律清成 `nil`，不留懸空參照。歸屬地的變更
不寫 `MoveEvent` —— 那是「應該在哪」的變更，不是位置變更。

## 8. 工程設定

### 專案結構（XcodeGen）

```
where-are-you/
  project.yml                    ← 進版控
  docs/SPEC.md
  Sources/
    App/         WhereAreYouApp.swift
    Models/      Node.swift, MoveEvent.swift
    Logic/       TreeQueries.swift（遞迴 / 缺件 / 循環防呆）
    Views/       HomeView, ContainerView, ItemDetailView, AddItemView, WhereIsItSheet
    Services/    LocationService, PhotoStore
  Tests/
  .gitignore                     ← 排除 *.xcodeproj
```

`.xcodeproj` **不進版控**，避免 pbxproj 衝突；`xcodegen && xcodebuild build` 即可驗證。

### 資料庫開不起來時

啟動時若 `ModelContainer` 建不出來（最常見的原因是裝置上留著舊 schema 寫出來的 store），
**把舊檔移到旁邊、用新的 store 再開一次**，不是直接當掉。移開時連同 `-shm` / `-wal`
一起搬，檔名加上時間戳。

**絕不刪除舊檔。** 理由與 §7 的刪除語意同一條：沒有雲端備份的情況下，一次啟動失敗
不該蒸發使用者的全部資料。移開之後資料還在檔案系統上，要撈得回來。

**為什麼不是直接當掉：**
schema 還在長的階段，這個情況是常態而不是例外。當掉的結果是一個打不開、也看不出
為什麼打不開的 app —— 使用者唯一能做的是砍掉重裝，那等於強制刪資料，比移開更糟。

移開之後仍然開不起來，才是真的壞了，那時才當掉並把原始錯誤印出來。

### 測試策略

只測邏輯層，用 Swift Testing + in-memory `ModelContainer`：

- 遞迴計數包含孫節點
- 缺件計算：離開子樹才算缺（含 §3.2 的橡皮擦反例）
- 外來件計算
- 移動到自己的子孫會被拒絕
- 刪除容器後子節點上移到祖父

不寫 UI Test — 對單人 MVP 太脆、太慢。

## 9. 視覺方向（v2）

> v1 曾走「iOS 原生為骨」，做出來太像系統設定 App，已作廢。
> 現行方向參考 Uber / Untitled UI / MiLi MiTag 的簡約語言。

**白底、Inter、零卡片、零分隔線、零 chevron。**

層級完全由**字重、尺寸與間距節奏**撐起，不靠灰底分組、不靠框線。
綠色只出現在三個地方：主按鈕、「在」狀態記號、移動歷史的當前節點。

| 決策 | v1（作廢） | v2（現行） |
|---|---|---|
| 底色 | 灰底 `#F2F2F7` + 白卡片 | 整面純白，無卡片 |
| 分隔 | 每列 hairline | 零分隔線，靠 56pt 列高與群組間距 |
| 字型 | SF Pro 全域 | Inter 走拉丁與數字，中文用系統黑體 |
| 列高 | 44pt | 56pt |
| chevron | 每列都有 | 全部移除，整列即觸控目標 |
| 群組標題 | iOS 區段標題 | 12/16 Semi Bold + 1.6 字距 |
| 表單 | 左標籤右值同列 | 標籤在上、值在下，底線一條 hairline |
| 歷史 | 條列 + 分隔線 | 左側時間軸，當前節點用強調色 |

### 不使用 emoji（硬規則）

介面、程式碼、文件一律不用 emoji。容器圖示、狀態指示、按鈕圖示全部走**向量字符**
（`Icon/Glyph` 元件，24×24 線性、可 tint、可綁 token）。

理由：emoji 無法 tint、深色模式下對比不可控、跨系統版本外觀會變、無障礙朗讀結果雜亂，
而且尺寸與線寬跟 SF Symbols 對不齊。使用者自訂容器的識別改用「圖示 + 強調色」，不用 emoji。

### Token（v2 實際值）

| Token | Light | Dark | 對比 |
|---|---|---|---|
| `bg/grouped`（畫面地） | `#FFFFFF` | `#0B0C0D` | — |
| `bg/field` | `#F3F4F5` | `#17191B` | — |
| `bg/elevated`（sheet） | `#FFFFFF` | `#16191A` | — |
| `text/primary` | `#111315` | `#F2F4F4` | 18.6 / 17.7 |
| `text/secondary` | `#6B7278` | `#9BA1A8` | 4.88 / 7.51 |
| `text/tertiary` | `#6F757B` | `#8A9198` | 4.66 / 6.14 |
| `text/danger` | `#C9251C` | `#FF6F63` | 4.84 / 6.38 |
| `border/separator` | `#EDEEEF` | `#212426` | 1.16 / 1.25 |
| `accent` · `state/ok` | `#2F6F4E` | `#4CAF7D` | 5.99 / 7.21 |
| `state/missing` | `#C9251C` | `#FF6F63` | 5.58 / 7.18 |
| `state/foreign` | `#6F757B` | `#8A9198` | 4.66 / 6.14 |

字級：Inter — Large Title 30/35 Bold · Title 2 21/27 Bold · Title 3 19/25 Semi Bold ·
Headline 17/23 Semi Bold · Body 17/23 Medium · Subhead 14/20 · Footnote 13/18 ·
Footnote Emphasis 13/18 Semi Bold（徽章專用）· Caption 12/16 Semi Bold +1.6 字距
（群組標籤與表單標籤專用）。

**為什麼徽章要單獨一個字級而不是共用現有的：**
`缺 2` 這種徽章要在一行掃視裡被抓到，Regular 的 Footnote 抓不住；Caption 的 +1.6 字距
是為了讓孤立的群組標籤撐開，用在兩三個字的徽章上會把膠囊撐得比內容還寬。
差一個字重就多一個 token，是因為 token 表是唯一能被機械對照的東西 —— 讓某個地方
「就直接寫 semibold」等於在這份契約上開一個洞。

**層級不靠亮度差，靠尺寸與字距。** `text/tertiary` 與 `text/secondary` 亮度接近是刻意的 ——
在零分隔線的版面裡，群組標籤是唯一的分組訊號，淡到看不清等於沒有分組。

**唯一刻意不合規的項目**：`border/separator` 對比 1.16。它是欄位底線與時間軸的裝飾性邊界，
不承載狀態辨識（標籤與值本身承載），拉高會讓畫面重新變得吵。這是有意識的取捨。
